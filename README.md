# Чек-анализатор: Telegram-бот «фото чека → траты по категориям → анализ трат»

Пользователь присылает фото кассового чека. Бот распознаёт позиции, суммы, категории, магазин и дату,
сохраняет чек в базу и отвечает на вопросы о тратах: отчёт за месяц с диаграммами, лимиты по категориям,
динамика цен, прогноз до конца месяца, поиск необычных трат, вопросы обычным языком.

Здесь описано устройство бота: как его запустить, проверить и доработать.

---

## 1. Быстрый старт

Требования: Windows или Linux, Python 3.12, **видеокарта NVIDIA с CUDA и ≥ 8 ГБ видеопамяти** (без неё бот
не запускается), ~10 ГБ на диске.

Окружение (Python 3.12, torch 2.6.0+cu124, transformers 5.22, peft 0.21, aiogram 3.31):

```powershell
uv venv --python 3.12 .venv       
uv pip install --python .venv\Scripts\python.exe torch torchvision --index-url https://download.pytorch.org/whl/cu124
uv pip install --python .venv\Scripts\python.exe -r requirements.txt
```

Запуск из папки проекта:

```powershell
.venv\Scripts\python main.py
```

Настройки — в файле `.env`:

| Переменная | Зачем |
|---|---|
| `BOT_TOKEN` | токен бота от @BotFather |
| `DEBUG_SAVE` | `1` — сохранять присланные фото в `debug_receipts/` для разбора ошибок; по умолчанию `0` |
| `BOT_HF_HOME` | необязательно: где лежит модель Qwen, по умолчанию `hf_cache/` внутри проекта |

Веса наших дообученных моделей (`vlm_lora_2b_cat/`, `vlm_lora_2b_cat_v2/`, `meta_lora/`, `query_lora/`,
`model_real/`, ~370 МБ) в репозитории не хранятся из-за размера. Их можно получить у авторов (распаковать
в корень проекта) или обучить заново командами из раздела 9.

Модель Qwen3.5-2B (~4,5 ГБ) лежит в `hf_cache/`. Если папки нет, при первом запуске модель скачается с
Hugging Face туда же, если есть — бот не обращается к Hugging Face (`HF_HUB_OFFLINE=1`). Это настраивает
`env_setup.py`, который импортируется первым во всех скриптах (до transformers).

Признак успешного запуска в консоли:
```
Загружаю модель распознавания Qwen/Qwen3.5-2B + адаптер ...\vlm_lora_2b_cat...
Подключён адаптер вопросов: ...\query_lora
Бот запущен
INFO Run polling for bot @check_categories_bot ...
```
Остановить — `Ctrl+C`. Во время работы бот занимает ~5 ГБ видеопамяти; одновременно с ним нельзя запускать
обучение (см. раздел 9).

## 2. Как это работает (общая схема)

```
фото ─► qr_reader: QR-код → точный итог, дата, признак возврата
     ─► Qwen3.5-2B + адаптер meta_lora → «это чек?» + дата покупки  ──► не чек → «Не похоже на кассовый чек»
     ─► Qwen3.5-2B + адаптер vlm_lora_2b_cat → позиции (название, сумма, категория) + итог
          · модель не уверена / сумма ≠ QR → пробуем повернуть фото на 90/270/180°
          · сумма меньше итога ровно на 1000·k → перечитываем адаптером vlm_lora_2b_cat_v2 («1 980,00»)
          · нет категории → классификатор rubert-tiny2 (model_real)
     ─► Qwen3.5-2B без адаптера → название магазина
     ─► SQLite (storage.py) → отчёты (reports.py), прогноз и необычные траты (forecast.py)

вопрос текстом ─► Qwen3.5-2B + адаптер query_lora → JSON-запрос ─► reports.answer_query считает ответ по базе
```

Принципы, которые важно сохранить при доработке:
1. **Честность.** Если модель не смогла прочитать чек или на фото не чек — бот так и говорит. Никаких запасных
   «угадываний» другими способами (старая схема EasyOCR + правила специально удалена). Сомнительный чек
   (сумма позиций не сходится с итогом или модель не уверена) сохраняется с пометкой «⚠️ требует проверки».
2. **Числа считает код, а не языковая модель.** Модель вопросов только переводит вопрос в запрос; суммы,
   средние, топы считает `reports.py` по базе.
3. **Один экземпляр весов Qwen в видеопамяти**, разные задачи — разные LoRA-адаптеры
   (`peft`: `load_adapter`, `set_adapter`, `disable_adapter`).
4. Всё работает локально, без платных и внешних сервисов (кроме самого Telegram).

## 3. Модели

Нейросети — **Qwen/Qwen3.5-2B** (картинка + текст, Apache-2.0) и **cointegrated/rubert-tiny2**.

| Компонент | Папка | Что делает | Как обучен | Качество |
|---|---|---|---|---|
| Qwen + **`vlm_lora_2b_cat`** | `vlm_lora_2b_cat/` | фото → `{"items":[{"name","price","category"}],"total"}` | LoRA r=16 на языковой части, 682 чека train-части датасета, 2 эпохи (`train_vlm.py --with-category`) | test, 151 чек: F1 по товарам **0,931**, сумма позиции верна **96,2%**, итог верен 95,4%. Исходная модель: F1 0,903, суммы 84% |
| Qwen + **`vlm_lora_2b_cat_v2`** | `vlm_lora_2b_cat_v2/` | то же, но лучше читает тысячи «1 980,00» | + 400 синтетических чеков с дорогими позициями (`make_synthetic_receipts.py`) | test F1 0,926; на чеках кафе исправляет потерянные тысячи, но сам по себе иногда приписывает лишнюю → только вторая попытка |
| Qwen + **`meta_lora`** | `meta_lora/` | фото → `{"is_receipt","shop","date","time"}` | 699 чеков датасета + 450 синтетических «не чеков» (`make_nonreceipts.py`), 2 эпохи (`train_meta.py`) | чеки приняты **100%**, не-чеки отклонены **99,2%** (исходная: 93,1%); дата верна **94%** (исходная: 89%). Магазин на чеках кафе хуже исходной → в боте используются только «это чек?» и дата |
| Qwen + **`query_lora`** | `query_lora/` | вопрос → `{"metric","period","category","text"}` | 3000 сгенерированных пар (`make_query_dataset.py`, `train_query.py`), только текст | 25 вопросов, написанных вручную: **88%** полностью верных запросов (до обучения 4%) |
| Qwen **без адаптера** | — | название магазина (`vlm_reader.read_meta`) | готовая модель | на фото из кафе точнее дообученной |
| **rubert-tiny2** | `model_real/` | название товара → категория | синтетика `data/products.csv` + 1619 реальных названий `data/real_items_labeled.xlsx` (`train_real.py`) | реальный test: accuracy **94,5%**, macro-F1 0,895 |
| **IsolationForest** | — (обучается на лету) | необычно крупные чеки пользователя | sklearn, по чекам пользователя (нужно ≥ 20) | — |

Категории (везде одинаковые): **еда, напитки, бытовое, здоровье, одежда, транспорт, развлечения, другое**.
Договорённости разметки: корм для животных и косметика → бытовое; сигареты, пакеты, цветы, электроника, услуги →
другое; пряжа, игрушки, билеты в музеи → развлечения; блюда в кафе → еда; кофе в кафе и алкоголь → напитки.

Почему Qwen, а не OCR: первая версия проекта (EasyOCR + Tesseract + правила разбора) давала F1 по товарам 0,28,
после доработки правил — 0,625; готовая Qwen3.5-2B сразу дала 0,903, дообученная — 0,931.

## 5. Распознавание чека подробно (`pipeline.process`)

1. **QR** (`qr_reader.read_receipt_qr`). Если прочитан — итог и дата берутся из него (точно); `n=2` → возврат.
   На датасете QR читается примерно на 64% фото.
2. **«Шапка»** (`vlm_reader.read_header`, адаптер `meta_lora`, один проход): вероятность «это чек» (по вероятностям
   токенов `true`/`false` в ответе), дата и время. Если QR нет и `p_receipt < 0.3` → статус `not_receipt`.
3. **Позиции** (`recognize`): адаптер `vlm_lora_2b_cat`, промпт `PROMPT_CAT` (JSON: name / price / category и total).
   - Отбрасываются: сумма ≤ 0 (модификаторы в кафе «-с кетчупом»), названия-заглушки «Товар», «Товар 1» (так модель
     «сдаётся» на не-чеках), служебные строки (скидка, бонусы, округление, итог, НДС, оплата).
   - `fix_lost_thousands`: если итог больше суммы позиций ровно на 1000·k → второй проход адаптером
     `vlm_lora_2b_cat_v2`; его ответ принимается, только если сумма сошлась с итогом.
   - Уверенность = средняя вероятность «содержательных» токенов ответа. Если < 0.85 или сумма ≠ QR → пробуем
     повороты 90/270/180° и берём самый уверенный вариант (или тот, что сошёлся с QR).
   - Оборванный JSON (очень длинный чек) — собираются все целиком записанные позиции (`ITEM_RE`).
4. **Категории**: если модель не дала категорию — rubert `model_real`.
5. **Магазин**: исходная Qwen без адаптера (`read_meta`); при сохранении почти одинаковые названия склеиваются
   с уже встречавшимися у пользователя (`storage.same_shop`).
6. `Result.needs_review` = сумма позиций ≠ итог (±1 ₽) или уверенность < 0.85.

Изображение перед моделью уменьшается до 1600 px по длинной стороне (`VLM_MAX_SIDE`).
Время: обычный чек 10–15 с, длинный (20+ позиций, второй проход) — до минуты на RTX 4070 SUPER. Модель работает
без оптимизированных ядер (flash-linear-attention, causal-conv1d) — под Windows они не поставлены.

## 6. База данных (`storage.py`, SQLite `data/expenses.db`)

```
receipts(id, user_id, created_at, purchased_at, shop, total,
         operation,     -- приход / возврат прихода / ...
         qr_fn, qr_fd, qr_fp, image_hash, items_key,   -- для поиска дублей
         date_source,   -- qr / receipt (прочитала модель) / sent (день отправки) / user (исправлено вручную)
         needs_review,  -- 1: сумма не сошлась с итогом или модель не уверена
         source,        -- photo / manual (трата без чека) / demo
         note)
items(id, receipt_id → receipts ON DELETE CASCADE, name, price, category,
      category_source)  -- model / user
limits(user_id, category, amount)   -- PRIMARY KEY (user_id, category)
```
- Новые колонки добавляются к существующей базе автоматически (`MIGRATIONS` в `connect()`).
- **Все запросы фильтруются по `user_id`** (Telegram ID) — пользователь не видит и не может изменить чужие чеки.
- Дубли: тот же QR (ФН + ФД), та же фотография (sha256) или тот же набор позиций за последние 14 дней.
- Чек-возврат учитывается в отчётах со знаком минус.
- `total` чека = сумма позиций; пересчитывается после каждого редактирования (`recalc_total`).

## 7. Интерфейс бота (`main.py`)

**Кнопки внизу экрана** (`MENU`): 📊 Месяц, 🧾 Мои чеки, ➕ Трата без чека, 🎯 Лимиты, 📈 Цены, ❓ Помощь.
**Меню команд** Telegram (`set_my_commands`): `/month [ММ.ГГГГ]`, `/history`, `/receipt N`, `/add [текст]`,
`/limits`, `/prices`, `/week`, `/export`, `/demo`, `/forget`, `/help`, `/cancel`.

Сценарии:
- **Фото чека** (обычное или файлом) → статус-сообщение с шагами («Ищу QR…», «Читаю позиции…», «Определяю
  категории и магазин…»), потом ответ: магазин, дата и её источник, позиции, суммы по категориям, сверка с итогом,
  номер сохранённого чека, предупреждения по лимитам. Кнопки «✏️ Редактировать» / «🗑 Удалить чек»; для
  сомнительных — «🔍 Проверить позиции» / «✅ Всё верно». Чеки и вопросы обрабатываются по одному
  (`recognize_lock`), остальные ждут в очереди.
- **Карточка чека** (`receipt_card`): позиции кнопками, «📅 Дата», «🏪 Магазин», «➕ Позиция», «🗑 Удалить чек»,
  «✅ Проверено», «⬅️ Все чеки». Позиция → «🏷 Категорию», «💰 Сумму», «✏️ Название», «🗑 Удалить позицию».
- **Ввод текстом после кнопки** (сумма, название, дата, магазин, позиция, лимит, трата без чека) — словарь
  `pending[user_id] = (вид, к_чему_относится, время)`. Сбрасывается через 10 минут, новым фото, любой командой,
  кнопкой меню или «Отмена».
- **Трата без чека**: «такси 450», «стрижка 1 500 вчера», «обед 450 12.11.2026». Категорию даёт rubert.
- **`/month`**: круговая диаграмма по категориям, столбцы по дням, сравнение с прошлым месяцем (для текущего
  месяца — с тем же числом дней прошлого), крупные покупки, лимиты, прогноз и необычные траты, напоминание
  о чеках «требует проверки», кнопки ◀️ ▶️ по месяцам.
- **Вопрос текстом** → `query_model.question_to_query` → `reports.answer_query`; в конце ответа бот пишет,
  как понял вопрос («🤖 Поняла вопрос так: сумма трат, прошлый месяц, напитки»).
- **`/demo`**: добавить/убрать демо-траты (только `source='demo'`, настоящие чеки не трогаются).
  **`/forget`**: удалить все чеки и лимиты пользователя (с подтверждением).

Префиксы `callback_data`: `open, ok, hist, item, icat, cat, iprice, iname, add, idel, idelok, date, setd, shop, sets,
del, delok, cancel, mon, lim, demo, forget`.

## 8. Аналитика (`reports.py`, `forecast.py`)

- **Прогноз**: по прошлым месяцам строится «кривая трат» — какая доля месячной суммы обычно потрачена к k-му дню;
  прогноз = потрачено / средняя доля, диапазон — по разбросу между месяцами. Нужны ≥ 2 прошлых месяца, иначе —
  по текущему темпу (начиная с 5-го дня). Крупные разовые чеки (в 5+ раз больше медианного) не масштабируются.
- **Необычные траты по категориям**: прогноз категории > 1,5 × медианы прошлых месяцев и разница > 1000 ₽.
- **Необычные чеки**: IsolationForest (признаки: log суммы, число позиций, день недели, час); показываются только
  крупные (> 2 × медианы).
- **Динамика цен**: один и тот же товар в одном магазине в разные дни. Не учитываются весовые товары, транспорт
  и изменения ровно в 2–5 раз (это другое количество штук: модель записывает сумму позиции, а не цену за штуку).
- **Лимиты**: 🟢 < 80%, 🟡 ≥ 80%, 🔴 превышен; предупреждения после каждого нового чека или траты без чека.

## 9. Обучение и воспроизведение

Все команды — из папки проекта, **при остановленном боте**: обучение занимает 6–8 ГБ видеопамяти, вместе с ботом
на 12 ГБ не помещается, а при переполнении Windows молча использует оперативную память и раздувает файл подкачки.

```powershell
# датасет чеков: скачать parquet-файлы из https://huggingface.co/datasets/cdek-ocr/receipt-ocr-ru (папка data/) в data\receipt-ocr-ru\
.venv\Scripts\python make_synthetic_receipts.py --n 400
.venv\Scripts\python train_vlm.py --epochs 2 --with-category --out vlm_lora_2b_cat                     
.venv\Scripts\python train_vlm.py --epochs 2 --with-category --synthetic data/synthetic_receipts.parquet --out vlm_lora_2b_cat_v2   
.venv\Scripts\python make_nonreceipts.py --n 450 --seed 11 --out data/nonreceipts_train.parquet
.venv\Scripts\python make_nonreceipts.py --n 120 --seed 99 --out data/nonreceipts_test.parquet
.venv\Scripts\python train_meta.py --epochs 2                                                           
.venv\Scripts\python make_query_dataset.py
.venv\Scripts\python train_query.py                                                                     
.venv\Scripts\python train_real.py                                                                      
.venv\Scripts\python evaluate.py --split test                                                           
```
Технические детали обучения LoRA (`train_vlm.py`, `train_meta.py`):
- LoRA r=16, alpha=32, только линейные слои языковой части (`language_model`), «зрение» заморожено;
- потери считаются только по токенам ответа (`logits_to_keep`): иначе таблица вероятностей по всему словарю
  (~250 тыс. токенов) для длинной последовательности с картинкой занимает до 2 ГБ и переполняет видеопамять;
- `torch.cuda.set_per_process_memory_fraction(0.9)` и пропуск примера при нехватке памяти вместо падения;
- сохраняется эпоха с наименьшими потерями на отложенных примерах.

## 10. Известные ограничения

- Магазин иногда читается неточно (гостевые счета кафе, реклама на чеке) — исправляется кнопкой «🏪 Магазин».
- Время покупки адаптер `meta_lora` часто не выдаёт (в разметке датасета оно редко) → 00:00, дата при этом верная.
- На фото с двумя чеками распознаётся один.
- Категории незнакомых товаров иногда ошибаются (вино → еда); исправления копятся в `data/user_corrections.csv`,
  автоматического дообучения на них пока нет.
- Чек-возврат без читаемого QR не распознаётся как возврат.
- Тестовые цифры получены на датасете, где ~40% чеков — одна столовая; на чеках других заведений качество ниже.
- Нужна видеокарта NVIDIA; на CPU бот не запускается.
- База и фото хранятся на компьютере, где запущен бот.

## 11. Как доработать

- **Новая категория**: поменять список в `vlm_reader.CATEGORIES` и `reports.CATEGORIES`, переразметить
  `data/real_items_labeled.xlsx`, переобучить `vlm_lora_2b_cat` и `model_real`.
- **Новый тип вопроса**: добавить метрику в `reports.METRICS` / `answer_query`, шаблоны в `make_query_dataset.py`,
  переобучить `query_lora`.
- **Новая кнопка**: обработчик `@dp.callback_query(F.data.startswith("префикс:"))` в `main.py`; доступ к данным —
  только через функции `storage.py` с `user_id`.
- **Проверка изменений распознавания**: `evaluate.py` (метрики) и `compare_models.py` (наглядно, рядом).
